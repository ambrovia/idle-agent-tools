# Clear first, summarise last, keep everything

As of autumn 2026, the field's best practice for long-running agents is a layered pipeline, not a single summariser. The prompt prefix stays stable and bulky tool output is spilled to files. Stale tool results are cleared in large batches. Only when that stops working is the old part of the conversation summarised, into a structured checkpoint that is updated rather than rewritten, written by the same model as a continuation of the cached prompt. The user's own words, durable rules, file state and a recent tail stay verbatim, and the full transcript stays recoverable. Nearly every harness surveyed ships a version of this, usually triggered at 80–92% of the window (Gemini CLI and Hermes at 50%). Amp's May 2026 reversal from handoffs back to automatic compaction marks the consensus. The measurements favour the cheap steps. Removing old tool outputs while keeping the agent's actions and reasoning matched LLM summaries at about half the cost on SWE-bench. Summarisation alone lost up to 11 points and lengthened runs by 13–15%. Clearing before summarising added 7.7–9.7 points on all three models in the largest controlled study. What fails is just as consistent: file state, user constraints and facts that exist only in tool output degrade first, losses compound over repeated compactions, and the damage shows up as re-fetching and extra turns rather than lower completion. For idle-harness, cached input at about 1/100 of the uncached price changes the arithmetic. A long cached context is cheap to carry and every rewrite of it is expensive, so compaction should be triggered by quality and the window, done rarely and deeply, and its summary call must reuse the cache. The recommended base default is a 200K-token trigger whose first pass clears old tool results and long write arguments down to half the trigger, leaving pointers the agent can follow, with a structured summary only when that is not enough. The first message, every human message and a 20K-token tail stay verbatim, the file and failure trail is computed from the record rather than asked of the model, and every compaction is recorded so that re-fetch rate, cache-break cost and paired replays can show whether it works.

## Nearly every harness now clears, summarises and keeps a way back

By October 2026, almost every harness ships automatic compaction plus a manual command, and they share one shape: a cheap, deterministic pass over old tool output; an LLM summary of the older history with recent turns kept verbatim; durable instructions re-read from disk rather than trusted to the summary; and the full transcript kept on disk or in a database as the record, with compaction rewriting only the view sent to the model.

**Claude Code clears older tool outputs first and summarises only if needed** ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). After a compaction it re-injects from disk the project CLAUDE.md, auto memory, the plan and the skill list. It also re-reads up to five recently touched files and re-injects invoked skill bodies within fixed token budgets ([Context window](https://code.claude.com/docs/en/context-window)). A 2026 source study describes five context shapers that run cheapest first before each call, with the LLM summary last ([Dive into Claude Code](https://arxiv.org/html/2604.14228v1)). Hermes, deepagents, Goose, Gemini CLI and Cline put the same kind of deterministic pass in front of their summarisers. The record-plus-projection architecture is now the norm across pi's session tree, OpenHands' event log, Cline's append-only canonical transcript, Hermes' soft archive and deepagents' on-disk history file ([Harness Engineering survey](https://arxiv.org/html/2609.00006); [Cline SDK](https://github.com/cline/cline/blob/main/sdk/ARCHITECTURE.md)).

The 2025 argument between continuous sessions and fresh-session handoffs has largely been settled in favour of continuity. In October 2025 Amp removed compaction in favour of handoff, calling compaction lossy and a cause of meandering threads ([Amp](https://ampcode.com/news/handoff)). Its May 2026 rebuild declared that **"handoff is out. Compaction is in."** It now compacts automatically at 90% full, and users complained on the one day it was switched off ([Amp Neo](https://ampcode.com/news/neo)). Anthropic's long-running harness needed context resets for Sonnet 4.5. It dropped them for continuous compaction once Opus 4.5 and 4.6 stopped wrapping up early near their believed limit, the behaviour Anthropic calls context anxiety ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The pro-compaction camp now treats the summary as an index rather than as memory. Amp's `read_thread` sub-agent uses compactions to orient itself but reads the original messages when exact details matter, after Amp found that even 1M-token threads gave poor answers ([Amp](https://ampcode.com/news/read-bigger-threads)). Cursor saves the chat history as a searchable file after summarising ([Cursor](https://cursor.com/blog/dynamic-context-discovery)), and VS Code Copilot appends a pointer to the on-disk transcript ([alexop.dev](https://alexop.dev/posts/how-vscode-copilot-chat-conversation-compaction-works/)). Fresh sessions survive for unrelated tasks and polluted contexts ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

**Reactive triggers cluster at 80–92% of the window.** Codex computes 90% in source and clamps any configured limit to at most 90% ([openai_models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs)). Amp compacts at 90% and deepagents at 85%, pi at the window minus a 16,384-token reserve, and Goose at the lower of 80% of the window and 225K tokens, which keeps requests below a provider's long-context price tier ([goose](https://goose-docs.ai/docs/guides/sessions/smart-context-management)). The outliers fire early. Gemini CLI compresses at 50% of the model limit ([chatCompressionService.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/context/chatCompressionService.ts)). Hermes' agent compressor also fires at 50%, but its gateway safety net was raised to 85% because 50% compressed on every turn of long sessions ([Hermes](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching?full=true)). Two 2026 shifts sit on top of these thresholds. The first is **background preparation**: VS Code starts summarising at a jittered 78–82% when the cache is warm and at 90% otherwise ([backgroundSummarizer.ts](https://github.com/microsoft/vscode/blob/main/extensions/copilot/src/extension/prompts/node/agent/backgroundSummarizer.ts)), and Copilot CLI starts at about 80% and blocks at about 95% ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management)). The second is **cache-aware timing**: Claude Code compacts idle sessions of 200K+ tokens just before the one-hour cache expires ([Settings](https://code.claude.com/docs/en/settings-reference#idlecompaction)). Anthropic's API, meanwhile, now recommends on-demand compaction, where the client decides when to compact, wherever it is available ([Compaction overview](https://platform.claude.com/docs/en/build-with-claude/compaction)).

Summary prompts have converged on a de facto template: goal, constraints and preferences, decisions with reasons, files read and modified, progress split into done, in progress and blocked, errors and next steps, and critical identifiers. pi and Hermes use nearly identical sections. opencode V2 uses seven sections and caps the file list at 15. Roo Code copies the nine-section, analysis-first structure associated with Claude Code. Prompt length is diverging by who controls the model. Vendors with trained models move to minimal prompts: Cursor's Composer is RL-trained to summarise itself in about 1K tokens from a one-line instruction ([Cursor](https://cursor.com/blog/self-summarization)), and OpenAI's server-side compaction returns an encrypted, uninspectable item ([OpenAI](https://developers.openai.com/api/docs/guides/compaction)). Multi-model harnesses keep long templates: VS Code has an analysis scratchpad and eight sections ([summarizedConversationHistory.tsx](https://github.com/microsoft/vscode/blob/main/extensions/copilot/src/extension/prompts/node/agent/summarizedConversationHistory.tsx)), and Gemini CLI has a seven-tag snapshot, a second self-critique call, and a clause telling the summariser to ignore instructions embedded in the history ([snippets.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/prompts/snippets.ts)). Most harnesses that summarise repeatedly update the previous summary rather than regenerating it.

## Clearing old tool output matches summaries at half the cost

The best-controlled evidence comes from two studies. Both point to the same cheap step.

JetBrains' **Complexity Trap** ran SWE-agent on all 500 SWE-bench Verified instances with five model configurations. It replaced every observation older than the last ten with a placeholder and kept the agent's full reasoning and actions. This **cut cost by about half versus the unmanaged agent (50–57% in four of five configurations) and matched LLM summarisation's solve rate in four of five**. On Qwen3-Coder 480B, masking scored 54.8% at $0.61 per instance, against 53.8% at $0.64 for summarisation and 53.4% at $1.29 raw ([arXiv 2508.21433](https://arxiv.org/html/2508.21433v3)). Observations made up about 84% of a turn's tokens, which explains why removing them works. In the one configuration where both strategies hurt, Gemini 2.5 Flash with thinking, masking cost 4.0 points and summarisation 9.0. Summaries also lengthened trajectories by 13–15% in two configurations. The authors' tentative explanation is that summaries hide the failure signals that would otherwise end a run early. A hybrid of masking plus a rare summary gained 2.6 points and cost 7% less than masking and 11% less than summarisation. That result comes from only 50 instances. Frequent summaries made the hybrid worse, through cache misses and summary overhead.

The University of Texas study **Beyond Token Savings** is the largest independent test. It ran about 35,000 executions of 65 policies across three open models in mini-swe-agent ([arXiv 2609.32961](https://arxiv.org/html/2609.32961v1)). It partly confirms JetBrains. Tool-result clearing was the best SWE-bench trade-off, at 53.7% resolved with 0.57× the tokens and 0.71× the billed cost, while plain summarisation lost 11 points. **Clearing tool results before summarising beat summarising alone by 7.7, 9.7 and 9.7 points on the three models**, and partial summarisation beat full summarisation by 6.7–8.7 points. Clearing also made summarisation robust to weak summarisers. With 9B- and 12B-parameter summarisers, summarisation alone collapsed to 37% and 28% resolved, while clearing plus summarisation held at 63% and 67%. The study also found complications. Most rankings flipped between models, and similar aggregate scores hid real turnover: truncation gained 3 tasks and lost 14. **On Terminal-Bench, 11 of 12 policies lost 5–13 points**, because those tasks have many short observations and trigger compression about nine times per run, against fewer than two on SWE-bench.

The industry has in effect adopted the hybrid. It did not adopt the paper's narrower conclusion that masking alone suffices. OpenHands had built masking, attention-based and amortised condensers, then consolidated on a rolling summary that forgets the older half of events. It reported 54% against 53% solved on an unspecified SWE-bench subset, with per-turn cost settling under half of baseline ([OpenHands](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)). When JetBrains tested masking inside OpenHands, the SWE-agent window of 10 degraded results badly and had to be retuned to 58 before it matched summarisation. **The right window depends on how verbose a scaffold's tool output is**, so any default needs tuning against the harness's own tools. Search agents show the same regime dependence. Masking's gain traces an asymmetric inverted U: it helps mid-capacity models with strong retrievers and collapses when the model is already saturated ([arXiv 2606.00408](https://arxiv.org/abs/2606.00408)).

Learned and optimised compression beats naive summarisation, but nobody has tested it against simple masking. ACON optimises the summariser's guideline by contrasting runs where full context succeeded and compressed context failed. It cut peak tokens by 26–54% at roughly matched accuracy on AppWorld, OfficeBench and multi-objective QA, where FIFO, retrieval and LLMLingua baselines lost 7–29 points on AppWorld ([arXiv 2510.00615](https://arxiv.org/html/2510.00615v2)). ACON also found that compressing history seldom lowers API cost, because of KV-cache overhead. CompactionRL trains execution and summarisation jointly and reports **5–7 points over inference-time compaction on the same base models** on SWE-bench Verified and Terminal-Bench 2.0 ([arXiv 2607.05378](https://arxiv.org/abs/2607.05378)). Cursor reports that its trained self-summary halves its internal compaction-error metric while using a fifth of the tokens ([Cursor](https://cursor.com/blog/self-summarization)). The implication for a harness that wraps arbitrary models is that a model never trained with compaction in the loop loses measurable accuracy when the harness compacts it, so structure in the harness has to carry more of the load.

Three complements have weaker evidence. **Verbatim compaction** in Woolford's transparent style keeps user and assistant prose verbatim, reduces tool calls to one-line signatures and drops outputs. It held planted-fact recall at 96.6–100% over eight compactions, while pi's default summary failed most sessions by the fifth or sixth ([arXiv 2610.20116](https://arxiv.org/html/2610.20116v1)); the author built the winning method, and it carried 57K tokens against pi's 21K. For **memory and notes**, Anthropic reported +29% from context editing and +39% with its memory tool, plus 84% fewer tokens on a 100-turn search, without giving the model, task count or baseline ([Claude blog](https://claude.com/blog/context-management)), while a controlled ablation of static AGENTS.md and CLAUDE.md files across 288 runs found no measurable correctness change ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)). **Sub-agent offloading** has only indirect support: Anthropic's multi-agent researcher beat a single agent by 90.2% at about 15× the tokens of chat, Anthropic itself calls it a poor fit for most coding ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)), and no controlled coding-benchmark ablation exists.

Every result above also has to be weighed against **context rot, which starts well inside advertised windows**. NoLiMa found 11 of 13 models below half their short-context score at 32K tokens ([ICML 2025](https://proceedings.mlr.press/v267/modarressi25a.html)). Du et al. measured 13.9–85% drops with perfect retrieval, even when distractors were replaced by whitespace, so length itself costs ([arXiv 2510.05381](https://arxiv.org/html/2510.05381v1)). Chroma found all 18 models tested degrade non-uniformly ([Chroma](https://www.trychroma.com/research/context-rot)). Each compaction event is also lossy. The UT threshold sweep found that **compacting less often raised success**: moving the trigger from 10K to 20K cut events from 4.85 to 1.15 per attempt and lifted summarisation from 50.7% to 62.7%. No study maps agent success against fill fraction across models. The defensible reading is to trigger at a moderate fill, remove the cheapest-to-lose content first, and make lossy summary events rare.

## Compaction loses files, constraints and its own history first

The measured losses concentrate in a few predictable places, and the first is file state. Factory scored three production compactors with probes on 36,611 production messages. **The artifact trail, meaning which files were created, changed or examined, was the weakest dimension for every compactor: 2.45, 2.33 and 2.19 out of 5** for Factory, Anthropic and OpenAI respectively. The overall scores were 3.70, 3.44 and 3.35 ([Factory](https://factory.com/news/evaluating-compression)). The study is vendor-run, reports no variance and uses an OpenAI judge, but the weak spot is the same across all three. Anthropic's own cookbook shows the pattern on a 329K-token research task: compaction preserved all three high-level probe facts and none of three obscure specifics ([cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)). Builders answer by tracking files outside the summary. Claude Code re-reads the five most recent files, and pi appends read and modified file lists computed from tool calls.

User constraints are the second casualty, and 2026 research reframed this as a safety problem. **Governance Decay found policy violations rising from 0% with the policy in full context to 30% after compaction, and up to 59% for some models**, across 1,323 episodes ([arXiv 2606.22528](https://arxiv.org/abs/2606.22528)). Violations stayed at 0% when the constraint survived the summary and reached 38% when it was dropped. Pinning constraints outside lossy compaction restored 0%. The paper also demonstrates an attack in which crafted content makes the summariser drop a policy. Woolford found summaries reword, narrow or reframe rules ([arXiv 2610.20116](https://arxiv.org/html/2610.20116v1)). Claude Code's issue tracker keeps receiving reports of custom instructions lost across compaction with no signal to the user ([#96422](https://github.com/anthropics/claude-code/issues/96422)). Anthropic's documented answer is that early instructions can be lost and persistent rules belong in CLAUDE.md, which is re-read from disk ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)).

Repeated compaction compounds both losses. pi's default summary failed in most sessions by the fifth or sixth compaction, while verbatim compaction held ([arXiv 2610.20116](https://arxiv.org/html/2610.20116v1)). ACE documented what it calls context collapse: one monolithic LLM rewrite shrank an 18,282-token context to 122 tokens and dropped AppWorld accuracy from 66.7 to 57.1, below the 63.7 achieved with no context at all ([arXiv 2510.04618](https://arxiv.org/html/2510.04618v3)). ACE avoids this by merging itemised bullets with non-LLM delta logic. That supports summaries that are updated in place, not regenerated. Real sessions do compact repeatedly. In a trace of about 4,300 Claude Code and Codex sessions, sessions that compacted averaged 3.7 compactions, with a p99 of 33 ([TraceLab](https://arxiv.org/html/2606.30560)). Amp's longest thread has been compacted more than 68 times ([Amp](https://ampcode.com/news/read-bigger-threads)). Single-compaction evaluations, which means most of them, understate long-session risk.

The cost of lost detail shows up as repeated work rather than as lower completion. In a controlled planning environment, **retrieval calls rose from 21 to 64 under 5× compression while completion did not change significantly** ([arXiv 2608.16370](https://arxiv.org/abs/2608.16370)). Compression nearly doubled steps in ACON's FIFO baseline, from 16.1 to 28.5 on AppWorld. Summaries lengthened SWE-agent runs by 13–15%. Claude Code shipped a fix for the agent treating its last pre-compaction actions as done, then retracting or redoing finished work ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). A long-open Codex report describes auto-compaction making the model forget it is mid-task and has edited files ([#5957](https://github.com/openai/codex/issues/5957)). For a harness judged by cost to an approved solution, this is the failure that matters most. It hides in turn counts and token totals, not in pass rates. Factory's conclusion follows: optimise tokens per task, not tokens per request.

Operational failures form a third group. Claude Code stops auto-compacting after a few attempts when one output refills context right after each summary ([Troubleshooting](https://code.claude.com/docs/en/troubleshooting)), and Cursor fixed turns stuck compacting on every step without freeing space ([changelog](https://cursor.com/docs/cli/changelog)). Compacting too early backfires as well: users of Claude Code's idle compaction complain that compacting far below the limit makes them pay again to redo lost work ([#102666](https://github.com/anthropics/claude-code/issues/102666)), and Cursor users saw summarisation at 10–20% of the window ([forum](https://forum.cursor.com/t/context-keeps-summarizing-at-10-20-of-total-context-window/163850)). Context anxiety, where Sonnet 4.5 wrapped up early near its believed limit, largely faded with later models ([Cognition](https://cognition.com/blog/devin-sonnet-4-5-lessons-and-challenges)).

One gap stands out. No study isolates whether agents re-try approaches that already failed after a compaction, even though practitioners name it as a common trap and propose external attempt logs and loop detection ([Tian Pan](https://tianpan.co/blog/2026/04/19/compaction-traps-long-running-agents)). Manus keeps failed actions in context for the same reason ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)).

Across builders, the lesson is that **anything that must survive compaction should not live only in the conversation**. That covers rules, constraints, file state, attempt history and plans. Harnesses that moved such state to files report fewer failures than those that only tuned the summariser prompt: re-read instruction files, progress logs, JSON feature lists, on-disk history and pinned constraint blocks ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

## A 100× cache discount makes every rewrite the expensive part

Agent workloads are overwhelmingly reads. TraceLab found a 95.7% prefix-cache hit rate across Claude Code and Codex. A median step reads about 120K prefix tokens, appends under 900 and emits a few hundred ([TraceLab](https://arxiv.org/html/2606.30560)). Manus reports an input-to-output ratio of about 100:1 and calls the cache hit rate its single most important production metric ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Any edit invalidates the cache from the edited position onward, in the order tools, then system prompt, then messages ([Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Compaction therefore always pays a rebuild. Claude Code's documentation says compaction invalidates the conversation cache layer by design and reuses only the system-prompt layer ([Claude Code caching](https://code.claude.com/docs/en/prompt-caching)).

Builders limit that rebuild in two ways, and harnesses split sharply on the first.

**The first is making the summary call itself a cache hit.** Claude Code sends the exact same system prompt, tools and history and appends the summarisation request as a final user message, so reading the whole history costs a fraction of its size ([Thariq Shihipar](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)). opencode V2, Letta's `self_compact` modes and Cline, which writes its summary as a tool call, do the same. pi does the opposite: it serialises the transcript as text and disables cache writes. The Complexity Trap's summary calls also saw almost no cache reuse.

**The second is breaking the cache rarely and in big chunks.** Anthropic's `clear_at_least` exists so that each clear is worth its cache write ([Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). SWE-agent's `polling` option batches its observation mask because the plain mask breaks caching on every query ([SWE-agent](https://swe-agent.com/latest/reference/history_processor_config/)). OpenHands forgets half the events at a time for the same reason ([README](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/README.md)). TokenPilot's cache-aware eviction schedule reports 56–87% lower cost than prior systems ([arXiv 2606.17016](https://arxiv.org/abs/2606.17016)).

A simple break-even rule shows why idle-harness's pricing changes the answer. Let *r* be the cached price as a fraction of the uncached price. When a context of *L* tokens is cut to *L′*, everything after the first changed message is billed uncached once (or at a premium, where the provider charges for cache writes). Each later turn then saves about *r* × (*L* − *L′*). Compaction pays for itself after roughly (tokens after the edit point) ÷ (*r* × tokens removed) turns.

Take a 400K-token context cleared to 150K, with the edit just after a 20K head. At Anthropic's standard *r* = 0.1 the rewrite pays back in about 5 turns; at idle-harness's *r* ≈ 0.01 it needs about 52. A 200K context cut to 100K needs about 80 turns at *r* = 0.01, while a 1M context cut to 100K needs about 9.

**At a 100× discount, compaction below a few hundred thousand tokens is justified by quality and the window, almost never by money.** A 200K cached context costs about as much per turn as 2K uncached tokens. This is my arithmetic from the published pricing structure, not a measured result, and it assumes the cache stays warm.

Four design consequences follow.

**First, rolling observation masking is a cache disaster at these prices.** Masking the eleventh-newest observation on every turn re-sends everything after it uncached every turn, perhaps 30K tokens, against about 2K equivalents for leaving the context alone. That makes the supposedly cheap policy roughly 15× more expensive in input than doing nothing. The Complexity Trap's large cost savings came partly from APIs with weak or no cache discounts: the authors note that one provider did not discount cache hits at all. Those cost results do not transfer to a 100× discount. Batched clearing does, because it pays the rebuild once per event.

**Second, the summary call must be a cache-reusing fork.** Re-serialising a 200K history pi-style costs roughly 100× the input of appending an instruction to the cached prompt.

**Third, cut deep.** The rebuild is proportional to the context left after the cut. A deep cut is cheaper per event and also happens less often.

**Fourth, a cache that has gone cold anyway is a free moment to compact.** Claude Code's idle compaction exploits exactly this, but its backlash shows the free moment should only be used when the context is already near the trigger.

Two constraints narrow the options further. idle-harness sends every provider's requests in the chat-completions format through OpenRouter (`idle-harness/src/model.ts`), so provider-native compaction is out of reach without a second wire format. That rules out Anthropic's compaction endpoints and OpenAI's encrypted items. And nothing in the research shows whether xiaomi/mimo-v2.6-pro was trained with compaction in the loop, or how its quality degrades between 100K and 1M tokens. The default should therefore lean on deterministic structure the harness controls. It should also use the same model for any summary, because caches are per model and small summarisers collapsed in the UT study.

## The recommended default for the idle-harness base

The base's compaction is the floor every harness inherits until its own turn does better, and it is what the plain turn runs when a harness's turn breaks. It should therefore be the best-evidenced pipeline that stays small and deterministic.

The current fallback, `fit` in `idle-harness/src/turn.ts`, already gets several things right. It shortens the oldest tool results first, keeps the system prompt, the first message and the newest messages, and trims well below the limit (to 70%), so it fires rarely. The trimmed context persists as the next context instead of being re-rendered, and the full text stays in the append-only record. It misses six things. There is **no default limit**, so an unconfigured harness grows until the provider refuses at 1M and the plain-turn takeover is refused too. There is **no step for when clearing is not enough**. The protected tail is **six messages** rather than a token budget aligned to turn boundaries. The **pointer into `record.jsonl` is hard for the agent to follow**, because each record line is a large JSON entry. **Write and edit arguments, which carry whole file contents, are left untouched.** And the 30,000-character `clip` in `tools.ts` makes a **lossy middle cut at tool-output time**, discarding the middle of a long output instead of spilling it.

### A 200K trigger that cuts to half

The base should check before every model call, after the turn has returned its context. That is the safe boundary, where every tool call has its result. The context size should come from the provider's reported prompt tokens for the last call plus a four-characters-per-token estimate for what has been appended since, as pi does. Today's chars/4 estimate over the whole JSON context remains as the fallback.

The default trigger *T* should be **200K tokens**, still configurable through the existing `contextLimit`, with a hard ceiling of the window minus a 64K reserve for output and reasoning. WorkOS argues pi's 16K reserve starves high-reasoning turns ([WorkOS](https://workos.com/blog/coding-agent-context-window-compaction-settings)).

No study maps success against fill fraction for any model, let alone MiMo, so 200K is a starting hypothesis that the measurements below are built to move. Three facts put it there. **Practice for long-horizon work clusters near it, whatever the advertised window**: the Claude API's 150K threshold, Goose's 225K cap, deepagents' 170K fallback, Cognition capping a 1M model at 200K, and real Claude Code and Codex steps around 120K. **Degradation inside advertised windows is documented across model families.** And **at 200K, the step that fires is the one with the least measured downside**: clearing old tool output matched full context in most studies, and the lossy summary only follows once about 100K of non-tool content has built up. At the few hundred output tokens per step TraceLab measured, that takes hundreds of turns, which is the rare-summary regime both studies favour.

The cost argument points the same way. A 200K context is cheap to carry at a 100× discount, while a lower trigger multiplies lossy, cache-breaking events, which is the failure Hermes hit at 50%.

### Four steps, cheapest first, each only if the last fell short

| Step | Fires when | What it does | Evidence |
|---|---|---|---|
| 0. Spill | Every tool result over 30,000 characters (today's clip size) | Writes the full output to `.sessions/<session>/spill/<call id>.txt`; the context gets the head, the tail, the line count and the path | Append-only, so free for the cache; Cursor's file-backed MCP outputs cut total agent tokens 46.9% ([Cursor](https://cursor.com/blog/dynamic-context-discovery)); deepagents, Copilot CLI, Cline and Gemini CLI do the same |
| 1. Clear | Context ≥ *T* | Outside the protected tail, oldest first, until the context is ≤ *T*/2: tool results of 200+ characters become a one-line stub (tool, short arguments, size, success or the first error line, spill path); write and edit arguments over 2,000 characters become a stub naming the file and the turn; reasoning fields of old assistant messages are dropped | Masking ≈ raw at half cost; clearing is the best SWE trade-off; deepagents truncates old write/edit arguments at 2,000 characters |
| 2. Summarise | Still > *T*/2 after step 1, or step 1 reclaimed < 10% of *T* | A cache-reusing summary of the head (everything after the first message and before the tail), updating the previous summary, with base-written blocks appended | Clearing before summarising +7.7 to +9.7 pp; partial beats full; rare summaries beat frequent ones |
| 3. Recover | The provider refuses the request as too long | Steps 1–2 with targets of 50%, then 35%, of the refused size; then the plain turn takes over as today | opencode's shrink steps; pi's single compact-and-retry |
| Guard | Context back over *T* within 3 turns, or two passes each reclaim < 10% | Stops automatic compaction for the session and tells the agent once | Claude Code's thrashing stop; OpenHands' `minimum_progress` of 0.1 |

Step 1 keeps every assistant message's text and every tool call, so the agent still sees what it did and in what order. It loses only the bulky results, which are one `read` away in the spill folder. A cleared result that was never spilled is written there at clearing time, so every stub points at a file the bare `read` tool can page through. Dropping old reasoning fields is the least-evidenced part of the step. The supporting study is abstract-only: pruning historical reasoning once state is in files and tool outputs raised reward from 0.699 to 0.718 with 25.5% fewer input tokens ([arXiv 2609.29875](https://arxiv.org/abs/2609.29875)). The step costs nothing extra for the cache because the batch already breaks it, but it should be measured.

The protected tail is the newest messages totalling about 10% of *T*, so 20K tokens at the default, never fewer than the last complete exchange. It starts at a user message, or at an assistant message whose tool calls all have results, so no call is separated from its result. This sits between pi's 20K, opencode's 15K and Hermes' 10–25K.

### The human's words and the trail stay outside the summary

Three kinds of content should never depend on the summariser, because they are exactly what summaries measurably lose. First, **the system prompt and tool list are never touched**, which preserves both the cache layer and any durable rules a harness has written there. Second, **the first message and every human-authored message stay verbatim**, including inbox items from people and other sessions, newest first within 20K tokens, the budget Codex uses for recent user messages ([compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)). In step 2 they are re-inserted as a verbatim block inside the summary message. Verbatim user prose is what held recall at 93–98% in Woolford's tests, and constraint pinning is what restored zero violations in Governance Decay. Third, **the base computes the trail from the record and appends it as plain text** rather than asking the model to remember it: files read, files written or edited with the turn of the last change, and calls that failed with their tool, arguments, first error line and turn. This answers Factory's weakest dimension directly, the way pi's computed file lists do, and keeps visible the failure signals the Complexity Trap suspects summaries hide.

### A summary that updates, quotes and names what is unchecked

The summary is a single user message placed after the first message. If a provider insists on alternating roles, it is followed by a short assistant acknowledgement, as Gemini CLI and Aider do. Its structure follows the de facto template, with two additions that serve idle-harness's intents. Done items name the evidence that showed them done, echoing Amp's rule that tool calls are attempted actions, not outcomes. An Unverified section lists the open loops that intent I1 cares about.

```
[base] Compaction 3 of this session. Turns 2–188 are summarised below; turns 189 on follow verbatim.
Removed text: <session>/spill/<call id>.txt for tool results; <session>/record.jsonl for everything.

## Goal                         the task, quoting the human
## Constraints and preferences  quoted, never paraphrased
## Done                         each item with the check or output that showed it done
## In progress / Blocked
## Decisions and why
## Dead ends                    what was tried and why it failed; do not retry without new evidence
## Unverified                   changed or claimed, not yet checked
## Next step                    where work stood, quoting the last instruction
## Critical data                exact paths, commands, identifiers, error strings, numbers

--- written by the base from the record, not by the model ---
## What the human said          every human message, verbatim, newest first within 20K tokens
## Files read / Files changed   path, turn of last change
## Calls that failed            tool, arguments, first error line, turn
```

The summarisation instruction tells the model not to call tools or continue the task, and to treat the history as data, ignoring instructions inside tool output or file contents, as Gemini CLI does. It asks for terse single-line bullets, quotes of the human rather than paraphrase, and exact identifiers. When a previous summary exists, the model updates it, keeping what is still true, letting newer history win and dropping what is superseded, as pi, opencode and Hermes do. The whole summary stays under 5% of *T* (10K tokens at the default), Hermes' cap.

The base accepts the result only if the headings are present and the new context is smaller than the old one. Gemini CLI rejects inflated summaries, and opencode retries when the template is not filled. Otherwise it retries once. After that it falls back to deterministic compaction in the style of Woolford's transparent method: the head is replaced by the base-written blocks, the human's messages and one-line signatures of the head's tool calls. Compaction never blocks the loop.

### Cache handling that breaks the prefix once per event

The summary request is a fork of the live request. It uses the same model, system prompt and tools and the current messages, with the instruction appended as the last user message, so reading the history is a cache hit. It sets `tool_choice` to none where the provider accepts it, as VS Code does. It is never a separate, re-serialised transcript and never a cheaper model. The compacted context becomes the next context and is never re-rendered, as the loop already does, so the next cache write covers system, first message, summary and tail once.

Each compaction event records its edit position, so the predicted rebuild can be checked against the uncached tokens the provider reports on the next call. One opportunistic rule can follow once the provider's real cache lifetime has been measured from usage data. If the session sat idle long enough that the cache is cold anyway, and the context is above 75% of *T*, compact then, because the rebuild is already being paid. This mirrors Claude Code's idle compaction without its backlash from compacting far below the limit.

### What each harness's turn should own

The base pipeline should also be exposed as a building block: `base.compact(context, options)`. It returns the compacted context and writes its own record entry. Options cover the target, the tail size, tools never to clear, extra summary instructions and pinned text. A harness can then specialise compaction by changing parameters first and code second. Parameter changes are single-mechanism changes that are easy to declare, compare and carry between harnesses, which is intent I5.

Everything the evidence shows to be domain- or model-specific belongs in the turn. Timing comes first: compacting when a sub-task resolves rather than mid-derivation let SelfCompact gain up to 18 points on math and 5–9 on agentic search at 30–70% lower cost ([arXiv 2606.23525](https://arxiv.org/abs/2606.23525)), while 86.5% of real compactions fire mid-loop ([TraceLab](https://arxiv.org/html/2606.30560)). LangChain found agents rarely trigger compaction on their own, so this is a habit a harness has to learn, not a default ([LangChain](https://www.langchain.com/blog/autonomous-context-compression)). The turn also owns per-tool policies, such as exempting retrieval or test output from clearing the way Gemini CLI exempts `read_file` and `grep`, or a batched rolling mask. Domain-specific summary sections, pinned invariants, re-reading recently changed files as Claude Code does, progress or memory files, sub-agents for exploration and a self-critique pass over the summary all belong there too. So does background compaction: Slipstream reports up to +8.8 points by validating summaries asynchronously, from an abstract-only source ([arXiv 2605.08580](https://arxiv.org/abs/2605.08580)).

The most interesting specialisation is ACON's. It optimises the compaction instructions themselves by contrasting cases where full context succeeded and compacted context failed. idle-harness's improvement loop and its one-turn replay supply exactly that contrast.

One consequence for retrospectives (intent I2): once a session has compacted, the retrospective must read the record rather than trust the context. The stubs and the summary header tell it where to look.

## Measurements that show whether compaction pays

Compaction's effect on task success sits at ±3–4 points in the studies above. On 30–50 tasks with one run per arm, a difference in success rate has to be roughly 20 points before it clears a 95% interval (my binomial arithmetic). Comparing success rates between compaction policies will therefore mostly return noise. The measurements should instead target compaction's mechanisms, which move by large factors and can be paired. Task cost and quality act as guardrails.

Every compaction should be written to the record as a building-block call, like `model` and `tool`. The entry names the trigger (threshold, overflow, turn or cold cache) and who ran it (the base or the harness's turn, with the harness version). It records tokens before and after, both provider-reported and estimated, and what was removed by kind, with counts and tokens: tool results cleared, arguments truncated, reasoning dropped, and the turn range summarised. It also holds the summary's tokens and the summary call's cost, the edit position, and the compaction's ordinal in the session. Every model call should keep cached and uncached input tokens as the provider reports them, alongside the cost the base already records.

| Signal | Computed from the record | What it tells | Precedent |
|---|---|---|---|
| Cache-break cost | Uncached input on the first call after a compaction, plus summary cost, against tokens reclaimed × remaining turns | Whether compaction paid for itself | [Thariq Shihipar](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/) |
| Cache hit rate | Cached ÷ total input per call, excluding compaction turns | Whether anything else breaks the prefix | [TraceLab](https://arxiv.org/html/2606.30560): 95.7% |
| Re-fetch rate | Post-compaction calls repeating a cleared call's tool and arguments, and reads of spill files | Whether clearing removed what the agent still needed | [Liu](https://arxiv.org/abs/2608.16370): 21 → 64 calls |
| Repeated failure | Post-compaction calls with the fingerprint of a pre-compaction failed call | Dead-end memory, which no study has measured | [Tian Pan](https://tianpan.co/blog/2026/04/19/compaction-traps-long-running-agents) |
| Elongation | Turns and cost from compaction to an approved solution, against replay or similar tasks | Whether summaries keep the agent going | [JetBrains](https://arxiv.org/html/2508.21433v3): +13–15% |
| Constraint restatement | A human repeating an earlier instruction after a compaction; reopened tasks | Whether the human's words survived | [Governance Decay](https://arxiv.org/abs/2606.22528) |
| Next-action agreement | Replay of the turn after each compaction with the uncompacted and compacted context; same action or not | Paired, per-event fidelity | [Slipstream](https://arxiv.org/abs/2605.08580) |
| Probe recall | Recall, artifact, continuation and decision questions generated from the pre-compaction record, answered from the compacted context | Which section loses information | [Factory](https://factory.com/news/evaluating-compression) |
| Thrash and fallbacks | Guard trips, rejected summaries, deterministic fallbacks | Whether the pipeline is stable | [Claude Code](https://code.claude.com/docs/en/troubleshooting) |
| Outcome by compaction count | Cost to approved solution and rated quality, split by 0, 1 and 2+ compactions per task | The final verdict, over many tasks | — |

The record already holds both sides of every compaction, so next-action agreement and probe recall need no new infrastructure beyond the planned one-turn replay. They give paired answers on small samples.

Three experiments follow from this. A **forced-compaction stress test** runs the existing eval scenarios with `contextLimit` set to 20–30K, so every task compacts several times; LangChain forced summarisation at 10–25% of the window for the same purpose ([LangChain](https://www.langchain.com/blog/context-management-for-deepagents)). A **trigger sweep for MiMo** replays late turns of long sessions with the context cleared to 100K, 200K and 400K and compares next-action agreement and probe recall, which is the cheapest way to find where MiMo's quality actually bends. A **policy comparison over normal work** sets clear-only against clear-plus-summary and reads the result through re-fetch rate, cache-break cost and cost to approved solution rather than success rate.

## Conclusion

The field has quietly redefined compaction. In 2025 it meant writing a good summary. In 2026 it means keeping a lossless record and sending the model a cheap, structured index into it. The summary has become the last and rarest step, and recoverability has become the safety net. idle-harness starts with what most harnesses had to retrofit: an append-only record, a turn that owns the whole context, and one-turn replay. Its best default is therefore unusually deterministic. It clears and points, computes the trail and quotes the human, and leaves the model to summarise only the part nothing else can shrink.

The steep cache discount adds a finding that goes beyond idle-harness. When cached input costs 1/100 of fresh input, the optimisation question flips from how small the context can be to how seldom it can be rewritten. The controlled cost comparisons were billed at a 10× discount or none, so the literature overstates the savings of frequent compaction and understates the penalty of rolling masks. Nobody has measured compaction at a 100× discount, and a self-specialising harness that records cache-break cost per event can. Compaction is also an unusually good first target for self-specialisation. Its parameters are few and declarable, ACON shows its instructions can be learned from contrastive failures, and replay measures it below the noise floor of task success. The first parameter to learn is the trigger, because how a given model degrades with context length is the largest unknown in the whole design.
